# Course figure scripts

This directory holds the Python scripts that regenerate every
**self-made** figure in the lecture notes (figures plotted from data
or drawn programmatically), together with the underlying data and
metadata. External-source figures (NASA mission imagery, panels
reproduced from published papers) are not regenerated by code; they
sit only in `book/<lecture>/figures/` next to the markdown.

The aim is provenance: for any self-made figure in the deployed book,
you should be able to answer in seconds:

1. Which `.py` script produced it?
2. What data file did the script read?
3. Where did each value in the data file come from, and on what date
   was it retrieved or recorded?
4. Which BibTeX key in `book/references.bib` should the figure cite?

`manifest.csv` is the index that ties figures, scripts, data files,
and citation keys together. Update it whenever you add or migrate a
figure. Every row names a script that generates its figure, so a
figure reproduced from a published paper has no row; its provenance
lives in the caption and its BibTeX key.

## Directory layout

```
scripts/figures/
  README.md                      <- this file
  manifest.csv                   <- figure -> script/data/citation index
  _shared/
    __init__.py
    style.py                     <- apply_style() + save_figure() (PNG -> AVIF)
    exoarchive.py                <- NASA Exoplanet Archive TAP fetcher
  L01_introduction/
    __init__.py
    fig_<short_id>.py            <- one script per figure
    data/
      <static-data>.csv          <- static datasets (planet masses etc.)
      <static-data>.json         <- sidecar metadata
      nasa_*_<figureid>_<YYYY-MM-DD>.csv   <- versioned live snapshots
      nasa_*_<figureid>_<YYYY-MM-DD>.json
  L02_formation_orbits/
  ...
  L14_synthesis/
```

A script lives in `scripts/figures/L<NN>_<lecture-slug>/` and is named
`fig_<short_id>.py`, where `<short_id>` matches the AVIF filename in
`book/<lecture>/figures/`. So
`book/01_introduction/figures/ss_mass_budget.avif` is produced by
`scripts/figures/L01_introduction/fig_ss_mass_budget.py`.

## Running a script

Activate the conda env that has matplotlib (the project's `proteus`
env works), set `PYTHONPATH` to the repo root, then run:

```bash
conda activate proteus
PYTHONPATH=. python scripts/figures/L01_introduction/fig_exoplanet_cumulative.py
```

The script will (a) fetch or load its data, (b) write a PNG, (c)
convert it to AVIF via ImageMagick, (d) place the AVIF in the right
`book/<lecture>/figures/` directory, and (e) print the data and figure
paths it touched.

Use matplotlib 3.11.1 to regenerate figures: text extents shift between
matplotlib releases, and the CI collision check
(`scripts/figures/check_figure_collisions.py`, run by the `check-figures`
job in `.github/workflows/book.yml`) pins that version.

## Conventions

### Script docstring

Every script's module docstring states:

- **Caption / figure id** in the form `Fig. X.Y / fig:short-id`.
- **Markdown source** path and approximate line of the `{figure}` directive.
- **Data** description, including the table or fact sheet it comes from.
- **Citation key** (or keys) in `book/references.bib`.

This makes the script self-documenting and lets you grep for the right
file from any of those four entry points.

### Data files and their sidecars

Every data file (`*.csv`, `*.json`, `*.npz`) sits next to its script
in `scripts/figures/<lecture>/data/`. Each data file is paired with a
JSON sidecar that records:

- `purpose`: which figure the data is for.
- `source`: human-readable provenance (e.g. "NASA Exoplanet Archive
  pscomppars table", "Lugmair & Galer 2003 LA-MC-ICPMS half-life").
- `source_url` or `endpoint`: where the data was pulled from.
- `retrieved_date` (and `retrieved_utc` for live downloads): when.
- `columns` or `column_descriptions`: what each column means and its
  units.
- `citation_key`: the BibTeX key the figure caption should cite.
- `license_note`: whether the data are public domain, restricted, etc.
- For live downloads, also `adql_query` (or equivalent) and `n_rows`,
  so the snapshot can be verified or reproduced.

### Live-data snapshots

For figures whose data evolves (NASA Exoplanet Archive, recent
mission catalogs), the data sidecar is overwritten on each run, but
the CSV is suffixed with the retrieval date and figure id so older
snapshots are preserved alongside new ones:

```
nasa_exoplanet_archive_pscomppars_exoplanet_cumulative_2026-05-08.csv
```

The CSV name pattern is
`<source>_<table>_<figure_short_id>_<YYYY-MM-DD>.csv`. The figure
caption in the markdown notes the access date in human-readable form;
the JSON sidecar carries the machine-readable timestamp.

### Static-data bundles

For figures whose data are static physical constants or fact-sheet
values (e.g. planet masses, half-lives), the data lives in a
**single** non-dated CSV/JSON pair (e.g. `solar_system_masses.csv` +
`solar_system_masses.json`). Updating these values requires editing
the script's `write_data()` function and rerunning, which refreshes
both the CSV and its JSON sidecar atomically.

### Caption convention

Every self-made figure caption ends with the sentence

> Course-original figure.

A fuller course-original credit can also name the data source, e.g.
"Course-original figure from the tabulated data of
{cite:t}\`Attia2026\`." The generating script is named in an HTML
comment on the line directly above the `{figure}` directive, so it is
visible in the markdown source but not on the rendered page:

```markdown
<!-- Generated by scripts/figures/L01_introduction/fig_exoplanet_cumulative.py -->
```

For external figures, the caption ends with the source attribution
(`Reproduced from {cite:t}`Author2020`.`) instead, and there is no
script comment.

A script that reproduces, redraws, digitizes, or annotates a
published figure or an external image is credited as external: the
caption keeps the source attribution and does not end with the
course-original sentence, but the script is still named in the HTML
comment above the directive.

### AVIF target resolution

The shared `save_figure()` helper writes the PNG at 200 dpi and then
converts to AVIF at quality 80 for text-heavy plots, 65 for
photographic content. Always size the matplotlib figure so that the
saved PNG is at least as wide in pixels as the `:width:` value in the
markdown directive; otherwise the browser will upscale and the
figure will look soft. The `output_files/figure_triage.py` helper
flags any AVIF that violates this.

## Adding a new figure

1. **Decide the slug.** Same string as the AVIF filename minus the
   `.avif` (e.g. `composition_bar`).
2. **Create the script** at
   `scripts/figures/L<NN>_<lecture-slug>/fig_<slug>.py`. Copy from an
   existing script as a template. Fill in the docstring, define the
   data, write `make_plot()`, and call `save_figure()` with
   `book/<lecture>/figures/<slug>.avif` as the output.
3. **Write the data**. If the figure plots data, save it under
   `scripts/figures/L<NN>_<lecture-slug>/data/` and write a JSON
   sidecar with the metadata listed above.
4. **Update `manifest.csv`** with one row for the new figure.
5. **Run the script** once to produce the AVIF.
6. **Credit the figure in the markdown**: end the caption with
   "Course-original figure." and put the script path in an HTML
   comment above the `{figure}` directive (see "Caption convention").

## Migration status

As of the initial reorganization, only the figures listed in
`manifest.csv` have been migrated to the new structure. Many other
self-made figures were generated by one-off Jupyter or matplotlib
sessions whose source code was not committed. Each of these should be
reconstructed into a script the next time it is touched, following
the conventions above.

If you are about to edit a self-made figure that has no script in
this tree, please:

1. Find a high-resolution PNG/PDF source (the existing AVIF if
   nothing else).
2. Identify the data: pin it down to a specific paper, fact sheet, or
   public catalog.
3. Write a `fig_<slug>.py` script using one of the existing scripts
   as a template.
4. Add a row to `manifest.csv`.

This is how the corpus migrates incrementally without a flag-day
rewrite.
